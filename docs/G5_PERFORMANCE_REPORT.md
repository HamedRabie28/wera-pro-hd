## 3. RAM Report — ذاكرة الخادم (RSS المقيسة من /proc)

| التشغيل | Baseline | Peak | بعد الاكتمال |
|---|---|---|---|
| 5,000 صورة (تهيئة) | 163,788 KB | 249,684 KB | 206,492 KB |
| 500 مكرر (تخطٍّ) | 203,380 KB | 235,876 KB | 205,892 KB |
| 50,000 صورة + استئناف بعد انهيار | — | 236,400 KB | 202,592 KB |
| **100,000 صورة + 3 انقطاعات** | — | **238,232 KB** | **203,976 KB** |

**الاستنتاج الحاسم:** الذروة عند 100,000 صورة (238MB) ≈ الذروة عند 5,000 صورة (250MB) — **الذاكرة لا تنمو مع حجم الدفعة**: المعالجة متدفقة (ترويسة ≤64KB + تدفيق SHA-256 بلا تحميل الملف كاملاً §6.1) والذاكرة تعود لقاعدتها بعد كل مهمة. لا تسريب متراكم.

## 4. «لا تعطيل POS بسبب الصور» — استجابة API أثناء الاستيراد الثقيل

من تحليل السجلات الأربعة لاختبار 100k (`latency_analysis_100k.txt` — 3,995 طلباً مطابقاً):

| المقياس | أثناء نافذة المعالجة الفعلية (18:07:52→18:40:41) |
|---|---|
| الطلبات المخدومة | 3,793 |
| p50 | **8.6 ms** |
| p95 | **16.0 ms** |
| p99 | **25.2 ms** |
| طلبات فاشلة (بلا 200) | **0** |

| نقطة النهاية (التي تهم المحطات) | العينات | p50 | p95 | p99 | max |
|---|---|---|---|---|---|
| `GET /api/v1/media` (صفحة المكتبة — مصغرات الكتالوج/POS) | 1,891 | 7.2ms | 11.4ms | 15.8ms | 163.5ms |
| `GET /api/v1/media/import-jobs/1` (حالة المهمة) | 1,893 | 9.1ms | 17.9ms | 26.4ms | 144.7ms |

وفي تشغيل 50,000 صورة: `GET /api/v1/media` × 609 عينة · p50=4.9ms · p95=9.2ms — النمط نفسه.

**الأبطأ في كامل الاختبار كان طلبات الرفع نفسها (POST .../files حتى 3.4 ثانية لدفعة 500 ملف = 1,400 ملف/دقيقة)** — وهي عمليات إدارية اختيارية للمخازني، ليست مسار بيع. أبطأ طلب قراءة (1138ms) وقع لحظة إعادة إقلاع بعد إيقاف متعمد. **مسار القراءة الذي تستهلكه المحطات بقي دون p99=26ms طوال اختبار ضغط 33 دقيقة.**

## 5. اكتشاف المكرر على المقياس

تشغيل مخصص (perf_dedup_500.json): إعادة استيراد 500 صورة قائمة بنفس البذور → **skipped=500 · done=0 · failed=0** في 3.04 ثانية — كل ملف مكرر تُشار إليه الأصل القائم ولا يُنشأ ثانٍ (§6.1: SHA-256 حكم «مطابق تماماً»). وفي قاعدة 100k: `distinct_sha = total = 100,000` — صفر أصول مكررة بعد مئة ألف رفع.
